# 优化与 Profile 原则

本项目仍处于执行架构可以调整的阶段。性能工作应当改进真实程序的整体执行成本，同时保持 safe Rust 与 JavaScript 可观察语义。下列五项核心原则决定什么需要证明、删除和测量；随后关于改造范围与局部回退的规则，防止我们过早停止有价值的方向。既有候选的 opcode、文件边界、接口和门槛只记录当次实验。

## 一、项目优化的五项核心原则

1. **守住语义，开放内部设计。** 异常顺序、所有权、释放时机、回落 PC、getter／Proxy／转换顺序、容量与 TDZ 行为必须正确；safe Rust 约束持续有效。当前 helper、事务边界、布局、内联注解和融合形态都是可修改的实现。新方案若需要替换或删除旧 helper、matcher、元数据、接口及其文档限制，应直接修改相关边界。改动越广，越需要清楚写出不变量、失效边界和针对性一致性验证。
2. **让已建立的事实随其有效期传递。** VM 构建、JS 发布、帧或区域进入时能确定的事实，应通过执行表示、接口和作用域交给消费者。事实失效时重新验证；值类型、对象状态、索引等仍会变化的条件继续动态检查。分别追求零热路径重复验证，以及静态不适用站点零额外准入派发。提前计算一个 flag，若执行器仍重复解码与验证，并未达到目标。
3. **降低基础执行成本，核算所有路径。** 优先考虑使普通操作普遍变便宜的设计。特化也可以使用，但须同时计算命中、动态失败、静态不适用、首次执行和代码体积的成本。新增一个快入口时，记录它在其他指令上新增了什么判断、搬运、调用和生成代码。成功路径少做工作与整体程序变快需要分别证明。
4. **用机器码和真实程序验证成本模型。** 写清候选要删除的检查、值搬运、调用、分配或派发；核对生成代码，测固定工作量、真实覆盖与最终结果。Profile 发现的局部热点提供假设，不能代替这些验证，也不能用符号采样占比给架构方向设收益上界。
5. **区分方向、候选和受测版本。** 某个候选的回退先触发归因：是方向本身的代价、当前表示、额外准入、编译器生成代码，还是测量波动？可以修改、组合、暂时保留在实验分支，或撤销该候选。撤销一个实现不自动关闭方向；已有收益也不自动证明扩展同类特化值得投入。方向的判断应考虑合理的替代实现和真实负载覆盖。

## 二、改造范围与性能取舍

**允许大范围改造。** 热点可能分散在普通指令、值表示、所有权、栈与帧、数组、调用、编译和派发之间。若根因跨越这些边界，就连同相关接口和状态表示一起设计。工作范围由预期能删除的重复工作及语义证明决定，不由当前模块边界或一次实验的最小 diff 决定。小实验用于隔离机制，不能替代所需的架构改造；旧设计限制妨碍新结构时，鼓励删除它及仅为它存在的代码。

**把性能当作有约束的整体优化问题。** A 路径明显改善、B 路径小幅回退，是正常的候选结果，不自动撤销 A。先确认差异可分辨，再按真实负载权重、项目目标、资源成本和后续修正空间评价净效果。对 v8-v7 总分，八项贡献按分数倍率的对数相加；每项各设一个不可交易的性能阈值，会错杀有价值的组合。大规模改造允许阶段性性能债务；记录受影响负载、幅度、原因、修复思路与累计状态，继续完成可能改变整体成本结构的部分。正确性问题立即修复。默认启用或宣称目标达成时，公开裁决整体收益、重要子项回退和未解决债务。

## 三、Profile 的五项原则

1. **Profile 用来提出和修正成本模型。** 先看真实负载的阶段、函数、PC、数据形态、调用点、命中与拒绝分布，再提出“删除哪项工作”的假设。采样热点是线索，不是允许优化范围；分散在多个符号中的基础执行成本可能有很大的合计收益。符号 self% 不能给语义机制设收益上界。
2. **把工作量与执行效率分开。** 固定工作量的退休指令、调用、分配和值搬运回答做了多少工作；cycles、分支／缓存事件及耗时回答执行这些工作有多贵。不能从指令下降直接推断耗时倍率，也不能从耗时变化直接归因于缓存或分支预测。核对生成代码、内联、spill、栈帧和代码体积，确认假设中的工作真的消失。
3. **同时观察局部机制与全程序结果。** 微负载和定向探针定位机制；真实子项验证覆盖；完整套件评估累计结果。记录普通路径、命中、动态失败、静态不适用和受影响但没有新增命中的负载。对基础架构改动，不能只从一个函数或一种 span 的覆盖率决定是否继续。
4. **让对照可复核，并按分辨率解释。** 记录源码、工具链、构建参数、二进制、负载、运行次数和机器环境；同一系列重建双方。使用 A/A 估计波动、交错 A/B 减少时间漂移，保留原始样本。固定迭代耗时、整进程计数与原版 V8 Score 分别命名。干扰使小幅时间差不可裁决时，明确标注；仍可依据语义、覆盖和可复现的机器码证据继续探索。
5. **让证据推翻候选设计，也让异常结果推动调查。** 真实负载未覆盖、已命中却仍昂贵、未命中路径变慢、子项出现回退，都应回到执行表示和成本模型检查。不能因为一个指标小、一次采样不显著、当前 Scope 很大，直接给方向设低收益上界；也不能因为目标远大就忽略确定的回退。将“尚未证明”“该候选失败”“该方向缺乏可行收益”写成不同结论。

## 四、决策节奏

探索阶段允许不完整的架构候选和阶段性性能债务，先证明语义与机制；短轮测量用于定位和迭代。集成阶段检查跨路径净成本和累计回退，针对异常作修正或明确取舍。准备默认启用及报告最终收益时，再用可复核的完整负载和同身份基线裁决。每轮设计时主动检查旧规格是否仍有价值；失去依据的内部约束和仅为它保留的代码应删除或改写。原计划中的百分比门槛、两轮停止规则和固定的候选 API 属于其历史实验，不自动适用于后续方向。
