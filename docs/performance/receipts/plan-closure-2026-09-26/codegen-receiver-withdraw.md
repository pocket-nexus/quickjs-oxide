# Receiver withdrawal: bounded plain-code inspection

This is a read-only comparison of the existing AArch64 plain release artifacts. It did not run the VM, build, or collect new counters. The exact `llvm-objdump --disassemble-symbols=SYMBOL BINARY` output is in `codegen-receiver-withdraw/`; `comparison.json` records offsets and first differences. The disassembler is Homebrew LLVM; the binaries' build receipts record Rust 1.96.0.

| --- | --- | --- | --- |
| `ddf12f8f`, `build-entry-revert/release/qjs.build.json` | `d53aaefb2664436c6c0e6c6c4de48140608876c6f149853bbf2362db9a20c50c` | 5,215 instructions; `sub sp, #0x750` | 938 instructions / 3,752 B; `sub sp, #0x1a0` |
| `5688c3e1`, `build-withdraw/release/qjs.build.json` | `d7d70af2ccb86cc97697885410f3d6169a97f621afa0483530dcf235742f468a` | 5,215 instructions; `sub sp, #0x750` | 942 instructions / 3,768 B; `sub sp, #0x1d0` |

At the same instruction offset, the entire `run::run` mnemonic sequence is identical. Of 5,215 32-bit words, 271 differ: 245 are `bl` displacement updates, 25 are `add` immediates, and one is an `ldr` immediate. All 245 calls still resolve to the same named callee or the correspondingly shifted dyld stub; their target addresses shift by 0 or `0x44`. Each of the 26 data-address immediates shifts by `0x40`. **Every conditional or indirect branch word in `run::run` is identical**, as are all its other machine words. The function starts `0x34` later in the withdrawal binary, so its absolute address and external call displacements change. This supports the narrower statement that the `run::run` dispatch and loop code shape did not gain an instruction or change its internal branch topology; it does not show equal I-cache placement or equal behavior of every callee.

The direct object-local helpers also retain their instruction shapes: `RunSlots::local` is 96 instructions on each side (four changed words: two global-address `add`s and two call displacements); `RunSlots::replace_local` is 104 on each side with the same four categories; `release_frame_binding` is 77 on each side with identical words. The one-million-iteration `object_move.js` loop repeatedly reads and writes local objects, whereas ordinary call installation happens at entry to `work`. `OrdinaryCall::install` itself does change: its receiver-copy owner guard raises the stack reservation by `0x30` and static length by four instructions; both versions retain one `SlotStore::peek`, two `copy_reference`, and two `release_frame_binding` call sites. Those static changes are not an observed per-iteration cost.

The existing `2026-09-26-task1-3/counters-capability.trace`, `counters-toc.xml`, and `counters-process.xml` do **not** resolve the cycle regression. The trace is a single older `target/release/qjs` `local_move.js` recording, terminated by its five-second limit, not a paired `ddf`/`5688` `object_move` trace. Its recorded table mode is `bottleneck bottlenecks EL0`; the three exported process rows carry the four bottleneck categories, not explicit branch-miss or cache-miss counts. The string `l1d_miss_sampling` appears in serialized plugin capabilities, but it is not the selected counting mode or a usable A/B event here. Thus the repeated cycle increase is an observation, while cache/branch/placement attribution remains unknown.

## Existing samples and what they decide

Both relevant fixed-work runs used serial `ABBA-BAAB`, eight samples per side, the same `object_move.js` SHA within a run, and `/usr/bin/time -l` whole-process counters. These are process totals, including startup and teardown. They are not PC-local counters for the loop.

| Existing series | Retired instructions (baseline → candidate) | Cycles (baseline → candidate) | Cycle result |
| --- | ---: | ---: | ---: |
| `receiver-entry-gate/results.json`, `ddf12f8f` → `2d0eca7f` | 1,468,437,628 → 1,468,869,472 (+0.029%) | 281,071,789 → 297,716,277 (+5.922%) | Baseline range 279,555,105–287,221,154; candidate 295,697,373–306,639,677: no overlap |
| `settled-parent-gate/results.json`, Parent `29560e08` → withdrawal `5688c3e1` | 1,456,771,876 → 1,468,450,081 (+0.802%) | 280,696,715 → 301,198,290 (+7.304%) | Baseline range 278,220,443–286,205,956; candidate 300,218,616–302,784,957: no overlap |

The prior same-binary `receiver-gate-aa/results.json` and `fixed-aa/results.json` used other builds (`5e3` and `c7`), so they are only measurement-resolution checks, not an A/A for `ddf` or `5688`. Their object-move alias-median cycle differences were +0.003% and −0.012%; their within-alias cycle min/max spans were at most 2.23% and 0.90%, respectively. The two comparisons above exceed those spans, and the eight cycle samples per side in each comparison do not overlap. This makes the **whole-process cycle regression a supported gate result** under the recorded interference, rather than a sub-2% change to call inconclusive.

Wall time is less suitable for exact magnitude here. The `receiver-entry-gate` candidate includes a 212.54 ms wall outlier; same-binary A/A wall spans reached 19.09%. The median cycles per wall nanosecond also changed between series (about 2.99 for `receiver-entry-gate` versus 2.44 for `settled-parent-gate`), while the two engines *within each series* were close. Neither the wall variation nor the process-wide instruction count identifies the hardware stall source. There is no directly paired `ddf` → `5688` run, so the exact delta of the extra receiver-copy guard itself is also not established.

The `settled-parent-gate` metadata records Apple M1, AC power and low-power mode off, but no pinned CPU core or per-sample frequency/temperature. It permits other same-host work and reports load averages 11.68/16.50/14.22. These limits weaken exact wall-time claims; they do not erase the non-overlapping cycle ranges in its serial balanced run. The workload SHA is the same `48359d0b…` with one million iterations and output `2`.

**Formal status:** It is appropriate to mark the *cause* of the extra cycles **unknown**. It is not appropriate to mark the observed Object cycle outcome **unknown** or claim the withdrawal fixed it. The `5688` backup still fails its Parent cycle gate. The same hot `run::run` and local-helper instruction shapes narrow the search to changed code placement or behavior outside those decoded bodies, but the existing data do not prove instruction-cache, branch-predictor, data-cache, or another specific cause.
