# New core, phase 0: baseline and guard rails

Phase 0 of the new core tracked in #122 fixes three things before any new-core
code exists: the comparison base every later phase reports against, the
language surface the new core does not carry, and the collector stress mode
phase 1 builds in from the start. [Phase 1](new-core-phase1.md) depends on all
three.

## 1. Comparison base

[`baseline.md`](baseline.md) records, for the current engine and QuickJS
2026-06-04 on the reference machine, the whole-process time and user-space
instruction count of every fixed workload:

- V8 v7 (8 items), Octane 2.0 (15 items) and AWFY (14 items), generated by
  [`suite_matrix.py`](../../scripts/benchmark/suite_matrix.py) from pinned
  upstream checkouts. Each program runs a frozen number of `run()` calls (V8,
  Octane) or the harness's default inner iterations (AWFY), reads no clock and
  prints one completion line, so every engine does identical guest work and
  stdout is checked exactly.
- The project's fixed probe matrix ([probes](probes/README.md)).

Both are replayed with `fixed.py --linux-counters --cpu 2` (see the
[benchmark tools](../../scripts/benchmark/README.md#fixed-work-v8-v7-octane-and-awfy-matrix)).
Every later phase reports against this table with the same programs, runner and
machine. A change to a frozen count or a pinned source commit starts a new
baseline and is never mixed with this one.

The adaptive upstream scores (the standing table in #122) stay the public
comparison, but they are not used for per-phase acceptance: an adaptive run
does a different amount of work on each engine, so its instruction count means
nothing and its time folds in the harness's own clock loop.

## 2. Language surface not carried into the new core

Decided by the maintainer on 2026-10-16. Each item becomes an entry in the
[deviation ledger](../deviations.md) when the new core replaces the current one;
the current engine keeps them until then.

| Feature | Behavior in the new core | What it removes |
| --- | --- | --- |
| `with` statement | Early `SyntaxError`, as in strict code | object environments in the scope chain; every identifier resolves at compile time to a register, a scope slot or a global |
| `Symbol.unscopables` | The symbol exists; nothing reads it | only meaningful with `with` |
| Local (direct) `eval` | `eval(src)` runs as indirect eval in the global scope; `new Function` is unchanged | scopes materialized as name maps, `arguments` and `var` injection into a caller; locals can live in registers unconditionally |
| Realms | One realm per runtime; no API creates a second context on a runtime; isolation uses separate runtimes | the realm pointer on function objects, the realm switch on calls, `GetFunctionRealm` |
| `Symbol.species` | `Array`, `%TypedArray%`, `Promise`, `RegExp`, `ArrayBuffer` and `SharedArrayBuffer` methods construct the intrinsic constructor; a subclass instance's `map`, `filter`, `slice`, `then` and so on return a base-class instance | an observable `constructor` / `@@species` lookup on every such call |

Usage. pocketjs, the first consumer, uses none of these: no `with`, no direct
`eval`, no `Symbol.species` or `Symbol.unscopables`, and every host (PSP, Vita,
3DS, ESP-IDF, the C and Rust embeddings) creates one context per runtime; the
"realm" in the pocketjs framework is its own application-instance term. Outside
pocketjs, `Symbol.species` matters to code that subclasses `Array` or `Promise`
and expects derived methods to keep the subclass, and to polyfills such as
core-js that probe for it: a bundle carrying core-js must be checked so that the
probe does not install slower JavaScript replacements for native methods.
Realms matter to hosts that sandbox plugins in separate contexts of one
runtime; such hosts use separate runtimes instead.

**Test262 cost**, from a static scan of the pinned suite restricted to the
features the current engine admits (about 83,500 eligible variants; the
authoritative count is 83,354). A variant is one test in sloppy or strict mode;
`with` and `Symbol.unscopables` only count their sloppy variants.

| Feature | Variants |
| --- | ---: |
| `with` | 362 |
| `Symbol.unscopables` | 44 |
| Local `eval`: `language/eval-code/direct` | 336 |
| Local `eval`: every test calling `eval(` not written as indirect eval | 1,830 |
| Realms (`cross-realm` feature or `$262.createRealm`) | 508 |
| `Symbol.species` | 550 |
| **Union, narrow `eval` count** | **1,738** |
| **Union, wide `eval` count** | **3,197** |

The true number lies between the two unions: many tests call `eval` at the top
level of global code, where indirect and direct eval behave alike. Against
today's 83,304 passes that is a pass rate within QuickJS's scope of about
95.9–97.6%, against 99.69% now. The exact variant list is produced by one full
Test262 run of the current engine with the five behaviors switched off, and is
frozen next to the Test262 admission data, so the phase 4 exit criterion ("back
to the v0.2.1 level minus dropped features") is a fixed number.

## 3. Collector stress mode

Phase 1 ([§4](new-core-phase1.md#4-garbage-collection)) builds a non-moving
mark-sweep whose only safepoints are allocations, and identifiers without
generations. A missed root therefore surfaces as a slot freed while still
reachable, and only if a collection happens to run at the wrong allocation. The
stress mode makes every allocation that point.

- **Activation.** The Cargo feature `gc-stress` compiles it in and sets
  `GcState.stress`: every allocation collects first. `GcState.stress_interval`
  (default 1) collects before every N-th allocation instead, for suites too slow
  at 1. Without the feature neither field exists, and release builds carry no
  check. From phase 2, when JavaScript runs, the CLI exposes the interval as
  `--gc-stress=N` in `gc-stress` builds.
- **Collection.** A full mark from the root set of phase 1 §4 (runtime roots,
  `RootStack`, handles, and from phase 2 on the register file and frame
  headers, from phase 4 on the `Trace` of pending native state machines), then
  sweep.
- **Poisoning and liveness.** Sweep clears the slot's bit in the arena's `live`
  bitmap and overwrites the record with a poison value of its type. Under
  `gc-stress` and in debug builds every arena access asserts liveness, so a
  stale index panics at the access that used it, not at a later unrelated
  corruption. Release builds do neither.
- **Verification after each collection** (`gc-stress` only): every marked slot
  is reachable from a root; no free-list entry is marked or live; every
  value-heap range belongs to exactly one live owner; every shape referenced by
  a live object, and every validity cell referenced by a live shape, is live.
- **What runs under it.** Phase 1: `cargo test -p oxide-core --features
  gc-stress` in CI for every change. From phase 2: additionally the fixed
  probes at smoke size and the V8 v7 programs at one `run()` per benchmark under
  `--gc-stress=1`, gating changes to the heap, the VM, natives that allocate and
  the embedding API; from phase 4 the focused Test262 vector under a larger
  interval nightly.

The current engine is reference counted and has no equivalent.
