2026-10-08，第 3 项 3a 三轮之后。测量版本 `cf47ccde`（与 `1caa9a5c` 同一棵树），x86 Docker Callgrind（Rust 1.88，带行号表的 release 构建）。

## 3. 句柄检查

**现状。** `object_fast`/`live_node_fast` 在 release 构建中**不核对代数**（代数检查 `assert_trusted_handle!` 只在 debug 构建生效）。剩下四项：`Vec` 下标边界、槽位状态是否 `Resident`、强引用计数是否非零、节点数据是否 `Object`。约 20 条中：

- **约 10 条是重复的。** `read_matched` 在 `depth == 0` 时对接收者再做一次 `object_fast`（`property_ic.rs` 读槽位那一行），而接收者在进入比较前已经查过。直接复用即可，不涉及安全合同。
- **约 10 条无法在当前约束下去除。** 去掉边界和状态检查只能用 `get_unchecked`/`unreachable_unchecked`，而工作区是 `unsafe_code = "forbid"`，`docs/parity.md` 明确要求保留这条 safe Rust 约束。
- **"帧内已认证句柄免检"不可行。** 在 safe Rust 中，类型系统无法证明一个 `ObjectId` 指向的槽位仍然存活；能省的只是重复检查，不是检查本身。除非重新设计对象存储（例如按类型分开的 arena，让"节点类型"检查消失），那属于第 6 项"对象记录体积"的范围，收益约 2–4 条，不值得为读取单独做。

**结论：** 不改安全合同。去掉重复的那次查找（约 10 条），其余保留。

## 4. 方案

| 方案 | 内容 | 预计（条/次） | 风险 | 建议归属 |
|---|---|---:|---|---|
| A. 去掉多余检查 | 复用接收者的 `ObjectData`；条目中的 realm 比较删除（缓存表与 realm 同在不可变的 `PublishedFunctionData` 中）；domain 比较删除（同一份数据只由本 runtime 的堆生成，入口已检查 `belongs_to_domain`），保留 debug 断言 | 15–20 | 低 | 第 3 项（3f） |
| B. 单态命中小函数 | 解释器先调用一个只处理"单态、自有数据属性"的叶子函数：参数为站点、接收者，返回值或拒绝；寄存器少、序言短；未命中再走现有的 `select_linked_data_into` | 30–40 | 中：新增函数会改变热代码布局，须用 `perf stat` 看 L1i 未命中，不能只看 Ir | 第 3 项（3f） |
| C. `promote_field` 快路径 | 数字、布尔、null/undefined 直接复制；对象只增加引用计数；原生函数提示只在 `keep_receiver` 时计算 | 10–15 | 低 | 第 3 项（3f） |
| D. 预解码站点下标与 atom | 链接时把站点下标写进 `GetField*` 的附加操作数，命中不再查偏移表和 atom 表 | 16–25 | 中：改变执行码格式与校验 | 第 5 项（预解码），在计划中写明 |

A+B+C 预计让一次命中从约 250 条降到约 160–190 条；加上 D 约 140–170 条。

## 5. 目标修正

≤8% 的目标在第 3 项内达不到：即使 A–D 全部完成，命中仍约 150 条，其中约 60 条（解释器衔接与压栈）属于解释循环本身，归第 5 项。建议：

- 3f 的验收：Richards、DeltaBlue 读缓存 self 占比各 ≤14%，且八项原生不劣（以 `perf stat` 周期与 L1i 未命中先筛，再跑完整原生 A/B）；
- ≤8% 改为第 5 项完成后的联合目标（读缓存 + 解释循环衔接），在第 5 项中重新核对。

## 6. 决定与实施（2026-10-08）

**决定。** 保持 `unsafe_code = "forbid"`；3f（A–C）在第 3 项内做；第 3 项读缓存目标改为 ≤14%，方案 D 与 ≤8% 移入第 5 项。
另外决定：受信快速访问中的强引用计数非零检查只在 debug 与 `checked-handles` 构建中进行，与代数检查同等对待。

**句柄检查的其余选项。** 在 safe Rust 下还评估了：

| 选项 | 结论 |
|---|---|
| 去掉重复的接收者查找 | 已做（3f-A） |
| 计数检查只在检查构建中进行 | 已做；八项 Ir 只降 0.1–0.2%，`s=o.x` 不变：计数与槽位状态相邻，读取几乎不额外花费，分支总被正确预测。原估“每次访问 2–3 条”偏高 |
| 槽位状态与对象类型用一个模式匹配 | 已做，与上一项同一提交 |
| `ShapeId` 打包为单次比较 | 未做：预计约 3 条，编译器很可能已把相邻两个 `u32` 合成一次比较 |
| 免去 revision 所需的 shape 访问 | **放弃**：shape 是否可原地修改按引用计数判定（`shape_strong_count == 1`），共享 shape 在其他对象释放后可能变成唯一并被原地追加，revision 检查不能省 |

**实施。** 见计划第 5 节“第 3 项结果”中的 3f 部分。
